以下方案以 “NovaChat 为统一交互基座，Agent / DE / Copilot 为三种差异化能力封装层” 为架构原则，按企业级旗舰版封版要求给出标准定义与实现范式。三个组件共享 NovaChat 的会话、身份、审计与上下文基座，但在**自主边界、责任归属、交付物形态**三个维度上严格区分，避免能力重叠与治理混淆。

# 企业级旗舰版封版方案：NovaAgent · NovaDE · NovaCopilot

**版本**：Enterprise Flagship v1.0-FINAL
**封版日期**：2026-11-25
**封版原则**：定义即接口，接口即治理边界；组件间能力不越界，治理不重复，交付物可验收。


## 一、总体架构定位：NovaChat 作为统一基座

NovaChat 在三组件中承担**会话层与上下文总线**的角色，不直接执行业务动作。它提供：

- **统一身份上下文**：用户身份、租户归属、角色权限在一次会话中传递至 Agent / DE / Copilot，避免各组件重复鉴权；
- **持久会话与上下文压缩**：跨轮次记忆、文件引用、任务状态在会话内保持连续；
- **审计埋点统一出口**：所有组件的工具调用、审批事件、交付记录经 NovaChat 的会话标识汇聚，确保可追溯性不因组件差异而断裂。

在此基座之上，三个组件按 **“自主程度 × 责任归属 × 交付契约”** 三层判据分叉：

| 维度 | NovaAgent | NovaDE | NovaCopilot |
|---|---|---|---|
| **自主程度** | 中—高（任务内自主） | 高（岗位内自主） | 低—中（建议 + 受限执行） |
| **责任归属** | 任务发起人 | 岗位持有者（组织角色） | 交互中的操作者 |
| **交付契约** | 任务结果 + 推理链 | 队列工作量 + 验收记录 | 建议 + 可撤销动作 |
| **NovaChat 角色** | 任务下发与结果回传通道 | 工单/队列接入与状态回传 | 内嵌于工作流的交互面板 |


## 二、NovaAgent：NovaChat + Agent 标准

### 2.1 标准定义（封版口径）

**NovaAgent 是一个在单次任务边界内具备自主规划与工具调用能力、但自主权随风险分级动态收束的智能体执行单元。** 其“标准”不是能力清单，而是一组**准入控制**：任何 Agent 在接入企业生产环境之前，必须逐项通过以下八项检查，缺一不可。

| 控制项 | 标准要求 | 封版判据 |
|---|---|---|
| **01 目的** | 任务有具体输出、明确 owner、书面边界 | 唯一验收标准是“看起来智能”则不合格 |
| **02 数据** | 明确数据来源、出境范围、保留期限 | 无法说清信息在何处终止则不合格 |
| **03 权限** | 每工具仅暴露该任务必需动作 | 以 prompt 作为唯一访问控制则不合格 |
| **04 审批** | 敏感动作有定义明确的人工复核点 | 审批对象模糊或范围过宽则不合格 |
| **05 可观测** | 可重建工具调用、返回、失败位置 | 事故后仅剩模型最终回答则不合格 |
| **06 验证** | 关闭依赖 Agent 自述之外的**外部信号** | 无文件/状态/记录可核验则不合格 |
| **07 异常** | 缺数据、阻塞、越界时有安全出口 | 系统“即兴发挥”以避免停止则不合格 |
| **08 运营** | 有负责人、消费限额、可降级/停止 | 无人知道供应商切换或事故时怎么办则不合格 |

**核心原则**：“Agent 说它完成了”不是验收信号。可验收的关闭条件只能是：文件存在且可打开、测试通过、记录状态变更至预期值、URL 可达、或来源可回溯。

### 2.2 实现方案

分层架构（三组件共享 NovaChat 接入层）：

```
┌──────────────────────────────────────────────────────┐
│ NovaChat 接入层：会话上下文 · 身份透传 · 审计标识    │
├──────────────────────────────────────────────────────┤
│ NovaAgent 编排层                                     │
│  · 任务解析与规划（显式 DAG，非纯 Prompt 驱动）      │
│  · 工具路由（MCP / REST / 内部 Connector）           │
│  · 风险分级路由器：LOW→自动 / MED→通知 / HIGH→审批  │
├──────────────────────────────────────────────────────┤
│ 执行层：沙箱化工具运行时（最小权限，按任务发放凭证） │
├──────────────────────────────────────────────────────┤
│ 验证层：外部信号检查器（文件/API状态/DB记录/测试）   │
└──────────────────────────────────────────────────────┘
```

关键实现约束：

- **编排确定性优先**：任务的关键执行路径以显式工作流（DAG）表达，LLM 仅在需要判断的分支节点介入，避免“全 Prompt 编排”导致的不可回滚与不可追溯；
- **工具边界强制**：工具调用在沙箱中执行，凭证按任务实例动态签发，会话结束后立即失效；
- **审批不可绕过**：HIGH 风险工具在 NovaChat 中弹出审批卡片，审批记录以独立事件写入审计流，不依赖 Agent 自身日志；
- **验证器独立于 Agent**：外部信号检查器作为编排层的兄弟模块运行，Agent 无权将其标记为“已验证”。


## 三、NovaDE：NovaChat + DE（数字员工）标准

### 3.1 标准定义（封版口径）

**NovaDE 不是“能力更强的 Agent”，而是一个被赋予组织岗位、持有任务队列、在统一治理下跨系统完成工作的数字化工作实体。** 数字员工与 Agent 的分界不在于技术复杂度，而在于**是否具备岗位形态**：

> Agent 是能力本身；数字员工是把 Agent 装进岗位外壳之后的产物。Agent 交出结果，数字员工对一条队列负责。

**NovaDE 的四要件（缺一不可）** ：

| 要件 | 标准要求 | 封版判据 |
|---|---|---|
| **岗位形态** | 持有某一职能（如“应付单据处理”“一线客服分流”），来什么处理什么，而非等待单一触发器 | 仍是“一个触发、一条固定路径”则不是数字员工 |
| **任务队列** | 拥有独立队列，工作可能跨小时/跨系统，周期可长 | 无队列则无法度量工作量与 SLA |
| **能力调用而非内嵌** | 业务能力从共享技能层调用，岗位不各自重造能力 | 每个新岗位需重造一遍能力则不合格 |
| **治理面向队伍** | 身份、权限、脱敏、审计在队伍层统一配置，不按实例逐配 | 规模上量后再补治理 = 一次迁移项目 |

参考 AI Worker Standard 1.0 的正式定义：数字员工是 “an AI work entity with an identity that persists across tasks, defined responsibilities, an authorization boundary, and deliverables that can be checked” —— 核心在于**跨任务持久的身份、可核验的交付物、以及明确的授权边界**，而非法律人格或永久进程。

### 3.2 实现方案

NovaDE 采用 **控制层 / 执行层 / 技能层** 三层分离架构，NovaChat 作为队列接入与人工交接的交互面：

```
┌──────────────────────────────────────────────────────────────┐
│ NovaChat 交互面：队列视图 · 交接通知 · 人工补录 · 验收确认  │
├──────────────────────────────────────────────────────────────┤
│ 控制层（DE Control Plane）                                   │
│  · 岗位注册表（岗位定义 · 责任边界 · 验收合约）              │
│  · 队伍级治理：SSO · 角色 RBAC · 租户隔离 · 审计            │
│  · 队列调度与 SLA 监控 · 用量与成本归因                      │
├──────────────────────────────────────────────────────────────┤
│ 执行层（DE Worker）                                           │
│  · 岗位实例：从队列领取任务，自主规划步骤                   │
│  · 跨系统操作：ERP / CRM / HRIS / 文档系统                  │
│  · 人工介入边界执行：自动 / 生成待审 / 转人工，边界写死     │
├──────────────────────────────────────────────────────────────┤
│ 技能层（共享能力池，版本化管理）                             │
│  · 系统操作技能（APA）· 文档理解技能（ADP）· 知识技能（ACX）│
│  · 第三方 MCP 技能接入                                       │
└──────────────────────────────────────────────────────────────┘
```

关键实现约束：

- **岗位定义先于技术配置**：部署 NovaDE 的第一步是书面回答四问——这个岗位拥有哪一项单一职能（尽量窄）、需要哪些数据与工具、何时必须升级给人、用哪两个核心指标度量成功。岗位定义作为注册表中的不可变合约版本化存储。
- **影子模式强制**：新 DE 上线前必须在 Shadow Mode 中运行至少 48 小时，生成应答与动作草案但不执行，经人工审核通过率达标后方可切换至 Draft / Auto。
- **人工介入边界固化为策略**：每一步的执行模式（Auto / Draft / Handoff）在岗位合约中声明，不在运行时由模型“判断要不要找人”。边界文档是治理部署与事故之间的唯一分界。
- **技能层共享**：流程变更在技能层修改一次，所有调用该技能的岗位同步继承，杜绝“每岗一版流程”的版本分裂。


## 四、NovaCopilot：NovaChat + Copilot 标准

### 4.1 标准定义（封版口径）

**NovaCopilot 是嵌入用户现有工作流、以“建议—确认—执行”为交互契约、始终将最终决策权保留给人类的增强型协作智能层。** 其标准聚焦于**嵌入性与可控性**，而非自主性。

参考 Microsoft Copilot Studio 的三框架划分，NovaCopilot 的封版定位落在 **“标准线束 + Copilot 聊天线束”的合取**上：

- **标准线束**：基于规则、可预测的对话，遵循预定义主题与规则，提供一致性回答；
- **Copilot 聊天线束**：扩展至用户日常工作界面，接入企业知识，但不替代用户做出不可逆决策。

**核心判据**：NovaCopilot 的输出是**建议**（suggestion）与**待确认动作**（proposed action），而非直接生效的变更。任何写入、发送、审批类操作在执行前必须经过显式的人类确认——在 Draft 模式下保存为草稿，在 Auto 模式下也保留可撤销窗口与审计记录。

### 4.2 实现方案

NovaCopilot 的架构以 **“嵌入层薄、治理层厚”** 为原则，避免 Copilot 变成另一个需要独立运维的孤岛系统。

```
┌──────────────────────────────────────────────────────────────┐
│ 嵌入面（NovaChat 渲染于工作流内）                            │
│  · 侧边栏 / 内联建议 / 命令面板                              │
│  · 会话绑定当前工作对象（文档/工单/记录）作为 grounding     │
├──────────────────────────────────────────────────────────────┤
│ Copilot 运行时                                                 │
│  · 意图路由：规则命中 → 标准线束；开放推理 → 推理线束       │
│  · 上下文构造：企业知识 grounding（仅注入用户有权访问的内容）│
│  · 动作提案器：生成 proposed action，不直接执行              │
├──────────────────────────────────────────────────────────────┤
│ 执行闸门（Human-in-the-loop Gate）                            │
│  · Draft 模式：动作保存为草稿，人工发送/提交                 │
│  · Confirm 模式：显式确认后执行，附撤销窗口                  │
│  · Read-Only 模式：仅分析报告，零外部写入                    │
├──────────────────────────────────────────────────────────────┤
│ 共享治理层（与 Agent/DE 共用）                               │
│  · Entra ID / 企业 IdP 认证 · 租户级策略 · OTel 可观测      │
└──────────────────────────────────────────────────────────────┘
```

关键实现约束：

- **Grounding 权限继承**：Copilot 检索企业知识时，以当前用户的身份与权限执行，不获得超出用户可见范围的任何内容。“以用户身份运行”是 Copilot 安全模型的第一原则，而非事后过滤。
- **规则引擎优先于模型**：在可预测的、结构化的交互场景中，标准线束的规则引擎先行；仅在规则未覆盖的开放问题上才升级至推理线束。这保证了高频场景的确定性与可计费性。
- **动作永不“静默执行”**：即使处于 Auto 模式，Copilot 发起的每一个外部动作都生成独立的可审计事件，并与 NovaChat 会话 ID 绑定，支持按用户、按动作类型、按时间段的全量回溯。
- **扩展通过声明式接入**：第三方能力以 REST API 描述或 MCP 服务器形式注册，运行时由 Copilot 根据用户意图路由，不在嵌入面中硬编码连接逻辑。


## 五、封版验收清单（Executive Sign-off Checklist）

以下清单为旗舰版 v1.0-FINAL 的**冻结验收项**。任一未通过，该组件不得进入生产封版。

| # | 验收域 | NovaAgent | NovaDE | NovaCopilot |
|---|---|---|---|---|
| A1 | 身份与租户隔离 | 会话级身份透传，工具凭证任务级签发 | 队伍级 SSO + 岗位 RBAC + 租户隔离 | 以用户身份 grounding，权限不提升 |
| A2 | 审计完整性 | 工具调用全量事件，独立于 Agent 日志 | 队列动作 + 人工交接 + 验收确认全链路 | 每个 proposed action 独立审计事件 |
| A3 | 人工介入点 | HIGH 风险工具强制审批卡片 | 岗位合约声明 Auto/Draft/Handoff 边界 | Draft / Confirm / Read-Only 三模 |
| A4 | 外部可验证信号 | 验证器独立运行，Agent 无权标记通过 | 交付物可核验（文件/状态/记录） | 动作结果可撤销、可回溯 |
| A5 | 异常安全出口 | 缺数据/阻塞时停止，不即兴绕过 | 岗位合约定义升级路径与兜底规则 | 规则未命中时降级至“无法处理”而非猜测 |
| A6 | 能力复用机制 | 工具注册表版本化 | 技能层共享，改一处全岗位继承 | 扩展以声明式注册，不硬编码 |
| A7 | 影子/灰度能力 | 支持 Dry-run 验证外部信号 | 强制 Shadow Mode ≥ 48h | Draft 模式作为默认上线模式 |
| A8 | 成本可观测 | 按任务实例的用量归因 | 队伍级用量与 SLA 看板 | 按用户/动作类型的计费与限额 |

**封版结论**：NovaAgent 的封版底线是**八项准入控制全部通过**；NovaDE 的封版底线是**四要件齐备且控制层先于规模到位**；NovaCopilot 的封版底线是**人工确认闸门不可绕过、grounding 权限不提升**。三者共享 NovaChat 基座与统一治理层，在自主性光谱上形成从“建议”到“岗位执行”再到“任务自主”的清晰梯度，互不替代，也互不留下治理真空。
